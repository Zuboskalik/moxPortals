# Лаборатория нестабильных порталов

Учебный полнофункциональный проект: лаборатория управляет нестабильными межмировыми порталами, оценивает риск их коллапса и не допускает опасных или бессмысленных действий над ними.

Монорепозиторий:
- [`/backend`](backend) — REST API, Laravel 11 + MySQL, PHPUnit
- [`/frontend`](frontend) — SPA, React + Vite + Tailwind CSS + Axios + React Query

Полная документация процесса: [specify.md](specify.md) (спецификация, US/AC) → [plan.md](plan.md) (архитектура) → [tasks.md](tasks.md) (пошаговый чек-лист реализации). Вкладка **AI Worklog** в самом приложении отражает реальный ход разработки этой сессии: промпты, решения, ошибки AI и их исправления.

## Быстрый запуск

Требования: PHP 8.2+, Composer, Node.js 18+, MySQL 8 (запущенный локально).

### 1. База данных

Создайте базу `moxPortals` в локальном MySQL (сервер `127.0.0.1:3306`, пользователь `mysql`/`mysql` — при иных реквизитах поправьте `backend/.env`).

### 2. Backend (терминал 1)

```bash
cd backend
composer install
cp .env.example .env
php artisan key:generate
php artisan migrate
php artisan serve
```

API доступен на `http://127.0.0.1:8000/api`.

### 3. Frontend (терминал 2)

```bash
cd frontend
npm install
cp .env.example .env
npm run dev
```

Приложение доступно на `http://localhost:5173`.

### 4. Демо-данные

Откройте приложение и нажмите **«Сбросить к демо-состояниям»** в шапке — это заполнит БД пятью порталами, покрывающими все ключевые сценарии (CRITICAL-риск, закрытый портал, портал с существами, безопасный к закрытию, «здоровый» портал).

Подробные инструкции и структура — в [backend/README.md](backend/README.md) и [frontend/README.md](frontend/README.md).

## Формула риска

```
Score = energy_level * 0.4 + (1 - stability) * 40 + (time_to_collapse < 15 ? 20 : 0)
```

`Score` округляется и ограничивается диапазоном `0..100`. Итоговый уровень риска:

| Score | Risk Level |
|---|---|
| `≥ 75` | CRITICAL |
| `50–74` | HIGH |
| `25–49` | MEDIUM |
| `< 25` | LOW |

Расчёт выполняется исключительно на backend ([RiskCalculator](backend/app/Services/RiskCalculator.php)) и никогда не хранится в БД — только вычисляется по актуальным данным при каждом запросе.

## Действия над порталом

| Действие | Эффект |
|---|---|
| **Stabilize** | `stability = 0.95`; `energy_level` −10%; `status = stabilized` |
| **Close** | `status = closed` |
| **Dispatch Observer** | `creatures_count += 1`; `status = under_review` |
| **Mark as Under Review** | `status = under_review` |

## Жёсткие бизнес-ограничения (HTTP 422)

Все три правила проверяются на backend как источник истины (фронтенд лишь дублирует их для UX — блокировкой кнопок):

| Правило | Код ошибки |
|---|---|
| Нельзя `Stabilize`/`Mark as Under Review` уже закрытый (`closed`) портал | `PORTAL_ALREADY_CLOSED` |
| Нельзя `Dispatch Observer`, если `Risk Level == CRITICAL` | `RISK_TOO_HIGH_FOR_OBSERVER` |
| Нельзя `Close` портал с `creatures_count > 0` без явного `force_evacuate=true` | `EVACUATION_REQUIRED` |

Любое нарушение возвращает `422` с `{ message, error_code, context }`, не изменяет портал и не создаёт запись в журнале — действие атомарно.

## Чек-лист ручной проверки (для проверяющего)

Выполните по порядку на чистом стенде (backend + frontend запущены):

1. **Сброс к демо-состояниям.** Нажмите «Сбросить к демо-состояниям» в шапке → подтвердите. Ожидание: сводка показывает 4 открытых / 1 критический / 1 закрытый портал, в списке появляются 5 демо-порталов с корректной цветовой индикацией риска (CRITICAL — красный, MEDIUM — жёлтый, LOW — зелёный).
2. **Запрет опасного действия (BR-2).** На портале «Врата Пепла» (CRITICAL) нажмите «Наблюдатель». Ожидание: в модалке — предупреждение о запрете, кнопка «Подтвердить» недоступна; действие не выполняется.
3. **Эвакуация перед закрытием (BR-3).** На портале с существами (например, «Звенящая Арка», 3 существа) нажмите «Закрыть». Ожидание: появляется предупреждение «⚠ Внимание: в портале 3 существа! Эвакуировать перед закрытием?»; без галочки кнопка недоступна. Отметьте галочку и подтвердите — портал закрывается, в журнале появляется запись с упоминанием принудительной эвакуации.
4. **Изменение риска после стабилизации.** На активном портале нажмите «Стабилизировать» и подтвердите. Ожидание: `stability` становится `0.95`, `energy_level` уменьшается на 10%, статус — «Стабилизирован», риск-бейдж пересчитывается, сводка наверху обновляется без перезагрузки страницы.
5. **Журнал событий.** Откройте раздел «Журнал событий» внизу панели управления. Ожидание: все выполненные действия присутствуют, отсортированы от новых к старым; клик по «Diff» раскрывает сравнение состояния портала до/после действия.

Дополнительно: вкладка **AI Worklog** должна отображать инструменты, метки времени, таблицу этапов, ключевые промпты, принятые решения, ошибки AI и чек-лист без ошибок в консоли браузера.
