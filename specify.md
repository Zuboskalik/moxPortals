# Спецификация проекта: «Лаборатория нестабильных порталов»

## 1. Обзор

**Тип проекта:** монорепозиторий
- `/backend` — REST API, бизнес-логика, хранение данных, журнал событий
- `/frontend` — SPA для операторов лаборатории: мониторинг порталов, действия над ними, дашборд, AI Worklog

**Домен:** лаборатория управляет нестабильными межмировыми порталами. Каждый портал обладает энергетическим уровнем, стабильностью и риском коллапса. Операторы стабилизируют, закрывают или отправляют наблюдателей в порталы, а система обязана не допускать опасных или бессмысленных действий (невозможные состояния).

---

## 2. Модель данных

### 2.1 Portal

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUID / string | генерируется системой, уникален |
| `name` | string | обязательно, непустое |
| `destination_world` | string | обязательно |
| `energy_level` | integer | `1..100` |
| `stability` | float | `0.0..1.0` |
| `time_to_collapse` | integer (минуты) | `>= 0` |
| `creatures_count` | integer | `>= 0` |
| `status` | enum | `active`, `stabilized`, `closed`, `under_review` |
| `created_at` / `updated_at` | timestamp | системные поля |

### 2.2 ActionLog (журнал событий)

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID / string | идентификатор записи |
| `portal_id` | string (FK → Portal.id) | к какому порталу относится действие |
| `action_type` | enum | `stabilize`, `close`, `dispatch_observer`, `mark_under_review` |
| `description` | string | человекочитаемое описание события |
| `previous_state` | JSON (snapshot Portal) | состояние портала до действия |
| `new_state` | JSON (snapshot Portal) | состояние портала после действия |
| `timestamp` | timestamp | момент выполнения действия |

---

## 3. Формула риска

```
Score = (energy_level * 0.4)
      + ((1 - stability) * 40)
      + (time_to_collapse < 15 ? 20 : 0)
```

- `Risk Score` — округляется и ограничивается диапазоном `0..100`.
- `Risk Level` определяется по `Risk Score`:

| Risk Score | Risk Level |
|---|---|
| `>= 75` | CRITICAL |
| `50 – 74` | HIGH |
| `25 – 49` | MEDIUM |
| `< 25` | LOW |

`Risk Score` и `Risk Level` — вычисляемые (derived) поля, не хранятся напрямую, а пересчитываются при каждом чтении/действии.

---

## 4. Действия над порталом

| Действие | Эффект |
|---|---|
| **Stabilize** | `stability = 0.95`; `energy_level -= 10%` (округление вниз); `status = stabilized` |
| **Close** | `status = closed` |
| **Dispatch Observer** | `creatures_count += 1`; `status = under_review` |
| **Mark as Under Review** | `status = under_review` (без иных изменений полей) |

Каждое действие обязано:
1. Пройти проверку бизнес-правил (см. раздел 5).
2. При успехе — записать событие в Action Log (`previous_state`, `new_state`).
3. При отказе — не изменять состояние портала и вернуть понятную ошибку с кодом причины.

---

## 5. Бизнес-правила / невозможные состояния (Edge Cases)

| № | Правило | Поведение при нарушении |
|---|---|---|
| BR-1 | Нельзя стабилизировать портал со статусом `closed` | HTTP 409 / ошибка домена `PORTAL_ALREADY_CLOSED`, действие не выполняется, лог не пишется |
| BR-2 | Нельзя отправить наблюдателя (`Dispatch Observer`), если `Risk Level == CRITICAL` | HTTP 409 / `RISK_TOO_HIGH_FOR_OBSERVER`, действие не выполняется |
| BR-3 | Нельзя закрыть портал (`Close`), если `creatures_count > 0`, без явного флага `force_evacuate=true` в запросе | HTTP 409 / `EVACUATION_REQUIRED`, если флаг не передан. При `force_evacuate=true` закрытие выполняется, а в `description` лога фиксируется факт принудительной эвакуации |

Эти правила проверяются **на бэкенде** как источник истины; фронтенд может дублировать проверки для UX (блокировка кнопок, подсказки), но не заменяет серверную валидацию.

---

## 6. Итоговая сводка (Dashboard Stats)

Агрегированные метрики по всем порталам, обновляемые в реальном времени/по запросу:

- Общее количество порталов, с разбивкой по `status`.
- Количество порталов по `Risk Level` (CRITICAL / HIGH / MEDIUM / LOW).
- Средний `Risk Score` по активным порталам (`status in [active, under_review]`).
- Суммарное количество существ (`creatures_count`) по всем не закрытым порталам.
- Список топ-N (например, 5) самых рискованных активных порталов.
- Количество событий в Action Log за последние 24 часа.

---

## 7. AI Worklog

Отдельный экран в UI, отображающий статические структурированные данные о процессе разработки с участием AI:

- Этапы разработки (например: "Проектирование модели", "Реализация API", "Frontend дашборд").
- Промпты, использованные на каждом этапе (краткое описание/текст промпта).
- Ошибки, допущенные AI в процессе (описание + как были обнаружены).
- Ручные правки (manual overrides) — что и почему было исправлено человеком после AI-генерации.

Формат хранения: статический JSON-файл (например, `frontend/src/data/ai-worklog.json` или `backend`-эндпоинт, отдающий тот же JSON), рендерится как читаемый таймлайн/таблица в UI. Данные не редактируются через UI — только через обновление файла/сида разработчиком.

Пример структуры записи:
```json
{
  "stage": "API: действия над порталом",
  "prompt": "Реализуй эндпоинты stabilize/close/dispatch_observer с проверкой бизнес-правил",
  "ai_mistakes": ["Не учёл флаг force_evacuate при первой реализации Close"],
  "manual_overrides": ["Добавлена проверка force_evacuate вручную после ревью"],
  "timestamp": "2026-09-15T10:00:00Z"
}
```

## 8. User Stories и Acceptance Criteria

### US-1. Просмотр списка порталов с уровнем риска
**Как** оператор лаборатории,
**я хочу** видеть список всех порталов с их текущим статусом и уровнем риска,
**чтобы** быстро оценить, какие порталы требуют внимания.

**AC:**
- AC-1.1: Список отображает `name`, `destination_world`, `energy_level`, `stability`, `time_to_collapse`, `creatures_count`, `status`.
- AC-1.2: Для каждого портала отображаются вычисленные `Risk Score` и `Risk Level`.
- AC-1.3: Список можно фильтровать/сортировать по `Risk Level` и `status`.
- AC-1.4: Порталы с `Risk Level = CRITICAL` визуально выделены (например, цветом/меткой).

---

### US-2. Стабилизация портала
**Как** оператор,
**я хочу** стабилизировать нестабильный портал,
**чтобы** снизить риск коллапса.

**AC:**
- AC-2.1: При успешном вызове `Stabilize` для портала со статусом, отличным от `closed`: `stability` устанавливается в `0.95`, `energy_level` уменьшается на 10% от текущего значения, `status` становится `stabilized`.
- AC-2.2: Если портал имеет статус `closed`, запрос отклоняется с ошибкой `PORTAL_ALREADY_CLOSED`, состояние портала не изменяется.
- AC-2.3: Успешное действие создаёт запись в Action Log с `action_type = stabilize`, корректными `previous_state`/`new_state`.
- AC-2.4: Неуспешное действие (BR-1) не создаёт запись в Action Log.

---

### US-3. Закрытие портала с защитой от опасной эвакуации
**Как** оператор,
**я хочу** закрыть портал,
**чтобы** прекратить его активность,
**но система должна помешать мне закрыть портал с существами внутри без подтверждения.**

**AC:**
- AC-3.1: Если `creatures_count == 0`, `Close` выполняется без дополнительных флагов, `status` становится `closed`.
- AC-3.2: Если `creatures_count > 0` и `force_evacuate` не передан или `false`, запрос отклоняется с ошибкой `EVACUATION_REQUIRED`, портал не изменяется.
- AC-3.3: Если `creatures_count > 0` и `force_evacuate = true`, `Close` выполняется, `status` становится `closed`, а в `description` лога явно указано, что закрытие произошло с принудительной эвакуацией.
- AC-3.4: Каждый успешный вызов `Close` создаёт запись в Action Log с `action_type = close`.

---

### US-4. Отправка наблюдателя с защитой от критического риска
**Как** оператор,
**я хочу** отправить наблюдателя в портал для сбора данных,
**но система не должна позволять это делать в критически опасных порталах.**

**AC:**
- AC-4.1: Если `Risk Level != CRITICAL`, `Dispatch Observer` увеличивает `creatures_count` на 1 и переводит `status` в `under_review`.
- AC-4.2: Если `Risk Level == CRITICAL`, запрос отклоняется с ошибкой `RISK_TOO_HIGH_FOR_OBSERVER`, портал не изменяется.
- AC-4.3: Успешное действие создаёт запись в Action Log с `action_type = dispatch_observer`.
- AC-4.4: Расчёт `Risk Level` для проверки выполняется на актуальном (текущем) состоянии портала на момент запроса, а не на закэшированном значении.

---

### US-5. Перевод портала в статус «на рассмотрении»
**Как** оператор,
**я хочу** вручную пометить портал как «под наблюдением» (`under_review`),
**чтобы** обозначить необходимость дополнительного контроля без изменения других параметров.

**AC:**
- AC-5.1: Действие `Mark as Under Review` меняет только `status` на `under_review`, остальные поля не затрагиваются.
- AC-5.2: Действие доступно для порталов в любом статусе, кроме `closed`.
- AC-5.3: Попытка пометить закрытый портал отклоняется с ошибкой (аналогично `PORTAL_ALREADY_CLOSED`).
- AC-5.4: Успешное действие создаёт запись в Action Log с `action_type = mark_under_review`.

---

### US-6. Просмотр журнала событий по порталу
**Как** оператор,
**я хочу** видеть историю всех действий, совершённых над конкретным порталом,
**чтобы** понимать, что и когда происходило.

**AC:**
- AC-6.1: Для каждого портала доступен список событий, отсортированный по `timestamp` (новые сверху).
- AC-6.2: Каждая запись показывает `action_type`, `description`, `timestamp`, а также diff между `previous_state` и `new_state`.
- AC-6.3: Записи в журнале неизменяемы (append-only) — их нельзя редактировать или удалять через UI/API.

---

### US-7. Просмотр сводного дашборда
**Как** руководитель лаборатории,
**я хочу** видеть агрегированную сводку по всем порталам,
**чтобы** оценивать общее состояние лаборатории без просмотра каждого портала отдельно.

**AC:**
- AC-7.1: Дашборд показывает количество порталов по каждому `status`.
- AC-7.2: Дашборд показывает количество порталов по каждому `Risk Level`.
- AC-7.3: Дашборд показывает средний `Risk Score` по активным порталам.
- AC-7.4: Дашборд показывает топ-5 самых рискованных активных порталов со ссылкой/переходом к деталям портала.
- AC-7.5: Данные дашборда пересчитываются при каждом запросе (или обновляются с обозначенной периодичностью), отражая актуальное состояние порталов.

---

### US-8. Просмотр AI Worklog
**Как** участник команды / проверяющий,
**я хочу** видеть структурированную историю того, как AI участвовал в разработке проекта,
**чтобы** понимать, какие решения принимал AI, какие ошибки допускал и что было исправлено вручную.

**AC:**
- AC-8.1: Экран AI Worklog отображает список этапов разработки в хронологическом порядке.
- AC-8.2: Для каждого этапа отображаются: использованный промпт (или его краткое описание), список ошибок AI (если были), список ручных правок (manual overrides, если были).
- AC-8.3: Данные загружаются из статического источника (JSON), не требуют отдельной формы редактирования в UI.
- AC-8.4: Если для этапа нет ошибок или ручных правок, соответствующие секции корректно отображают пустое состояние (например, «Ошибок не зафиксировано»), а не ломают вёрстку.

---

### US-9. Защита от невозможных состояний на уровне API
**Как** разработчик системы,
**я хочу**, чтобы все бизнес-правила (BR-1, BR-2, BR-3) проверялись на backend независимо от frontend,
**чтобы** невозможные состояния (например, стабилизация закрытого портала) не могли возникнуть даже при прямом обращении к API.

**AC:**
- AC-9.1: Каждое из правил BR-1, BR-2, BR-3 покрыто серверной валидацией и не может быть обойдено запросом напрямую к API (минуя UI).
- AC-9.2: При нарушении правила API возвращает структурированную ошибку с машиночитаемым кодом (`PORTAL_ALREADY_CLOSED`, `RISK_TOO_HIGH_FOR_OBSERVER`, `EVACUATION_REQUIRED`) и человекочитаемым сообщением.
- AC-9.3: Нарушение правила не создаёт запись в Action Log и не изменяет состояние портала (полная атомарность операции).

---

## 9. Нефункциональные требования (кратко)

- Все вычисления `Risk Score` / `Risk Level` выполняются на backend; frontend только отображает полученные значения (единый источник истины).
- API — REST, JSON, с понятными кодами ошибок домена (см. раздел 5, 9).
- Структура монорепозитория: `/backend` (API + бизнес-логика + хранилище), `/frontend` (UI: список порталов, карточка портала с действиями, дашборд, журнал событий, AI Worklog).
